# 要件（main）

## はじめに

この仕様は、空席が出た飲食店の店主が、手元のスマホから短い操作で、近くにいて嗜好の合う登録客へ特典つきの「今なら空いています」を Web プッシュで届け、その配信を人手なしで段階的に広げて上限で止めるウェブアプリ（AI HACK 2026 に出す軽いデモ）を実現する。

意図の段の成果物 `intent.md` の受け入れ基準 1〜17 と「本人が決めること（効果を示す数字）」、聞き取りの段から持ち越された4件（「近くにいる」がいつの位置か／オファーの有効期限／提出の形の帰属／店主のログインと初期設定）、本人判断に回った指摘1件（公開リポジトリの秘密情報の基準に帰属の印が無い・`audits/intent-c3-e1.audit.json` の F1）に対応する。対応表は末尾。

直した履歴: 第1周の監査（`audits/requirements-c1.verdict.json`）の直すべき指摘 F1（第1波の人数が上限を超える）、本人判断に回って「直す」となった F2（「人が読める形」が検査できない）・F3（候補が10人未満のときの第1波）、持ち越し4件（帰属の印の抜け／反応・待ち時間・徒歩圏の食い違い／許可の方法が検査できない／1行に複数の振る舞い）、反論記録の採点への異議（検査の段の付け方が揃っていない）と、本人の回答（`02_題材と注文.md` の3節「要件の段の第1周のあとの回答」: 反応の定義／店側の保護／入口の検査落ち）を反映した（2026-09-19）。

帰属の印は intent.md と同じ3種類。「本人発案」「本人選択」は元の文書にある本人の決定。推測で埋めた箇所には intent.md と同じ印を付ける（後で覆されうる。承認のときに本人が件数ごと確認する）。**本人がまだ決めていない分岐は、既定を1つ選んで印を付けたうえで、選ばなかった案を各要件の「補足」に残す。** 印は文の途中（値のすぐ後ろ）に置く。印を付けるのは**この文書で新たに決めたこと**で、intent.md で既に印つきで承認された決定を写しただけの箇所（例: 位置の扱い・秘密情報・README）には繰り返さない（対応表で intent.md の印へ辿れる）。

検証の段の付け方（この文書で揃える規則）:

- **段1**: 検査の基盤（単体テスト・状態遷移のテスト）で決定論的に合否を出せるもの。**時間の基準は、システムが自分で決める間隔・期限（取り直しの間隔・有効期限）なら段1**（設定値と振る舞いを検査できる）
- **段2**: lint・スキーマ・設定ファイルの検査で出せるもの（依存の名前・秘密情報の走査）
- **段3**: デプロイ先・実機・外部サービス（LLM・プッシュサービス）を通さないと分からないもの。**時間の基準でも、外部サービスの応答を含むものは段3**
- **段5**: 本人が目で見て決めるもの（操作の少なさ・見た目）。**ブラウザの描画（幅・横スクロール）は決定論で測れるが、ブラウザを動かす検査基盤を軽いデモに持ち込まない（AI判断）ので段5に置く**

用語（この文書で揃える語）:

- **店主**: 店側の画面を操作する人。**客**: 嗜好と位置を登録して通知を受け取る人。**システム**: 作るウェブアプリ全体
- **オファー**: 店主が1回の送信で作る「空席数＋特典＋有効期限」のひとまとまり。状態は「進行中」か「終了」の2つ
- **波**: オファーの配信を段階的に広げる1回分。**配信**: 1人の客へ通知を1通送ること
- **開封**: 客が通知からオファー画面を開くこと
- **反応**: 客がオファー画面で「行きます」を押すこと（本人選択）。次の波を出すかの判定に使う
- **来店**: 客がオファー画面で「特典を使う」を押すこと。反応とは別の数（本人選択）
- **購読**: 客の端末が通知を受け取るための登録。**鍵**: 推測できない文字列で、店や客の要求を見分けるもの

### 要件 1: オファーを出す（空席の入力と特典）

**目的:** 店主として、空席数と特典を短い操作で入れてオファーを出したい。それにより、席が空いたまま時間が過ぎる前に近くの客へ声を掛けられる

#### 受け入れ基準

1. 店主が空席数と特典プリセットの1つを選んで送信した時、システムはオファーを1件作成して進行中にすること［段1］
2. 店側の画面を開いた時、システムはその店の特典プリセット3つを1タップで選べるボタンとして表示すること［段1］
3. 空席数が1以上20以下（範囲は AI判断）の整数でない場合、システムはオファーを作らず入力の誤りを店主に示すこと［段1］
4. 特典が選ばれていない（特典を必須にするのは AI判断）場合、システムはオファーを作らず特典の選択を求めること［段1］
5. その店に進行中のオファーがある間（1店につき進行中は1件までとするのは AI判断）、店主が新しいオファーを送信した場合、システムは新しいオファーを作らず、進行中のものを止めてから出すよう店主に示すこと［段1］
6. 店主が店側の画面を開いてからオファーを出すまでに必要な操作は、空席数の指定・特典の選択・送信の3つだけ（尺度は AI判断）であること［段5］
7. 店側の画面は、スマホの画面幅 375px（幅の値は AI判断）で横スクロールなしに全部の操作ができること［段5］

補足:

- 「残席0」は要件2の専用ボタンで行い、空席数の入力欄に 0 を入れる操作ではない（intent 基準3で要件の段に回されたもの。AI判断。理由: 空席数はオファー作成時の値で配信総数の上限〔要件7〕の元になるため、後から書き換えると上限の意味が変わる）
- 空席数の入力の形（増減ボタンか数値入力か）は設計の段で決める
- 基準7を段5に置く理由は「はじめに」の段の付け方の規則

### 要件 2: 配信を止める（残席0）

**目的:** 店主として、席が埋まったらその場で配信を止めたい。それにより、満席なのに通知が届く体験を防げる

#### 受け入れ基準

1. 店主が「残席0」ボタンを押した時、システムはそのオファーを終了にして以後の波を出さないこと［段1］
2. 「残席0」の操作の後、システムはまだ送信していない通知を送らないこと［段1］
3. 「残席0」の操作の後、システムは店側の画面に「終了」と最終の配信数・反応数・開封数・来店数を表示すること［段1］
4. 終了したオファーに対して客が「特典を使う」を押した場合、システムは特典を無効として扱い来店に数えない（AI判断）こと［段1］

補足:

- 満席を人手なしで知る仕組み（来店数で残席を減らすなど）は作らない（本人選択・intent 基準3）
- 基準4の選ばなかった案: 終了後も有効期限内なら特典を使えるようにする（通知を見て向かっている客を救えるが、店主の「止めた」と客の画面の「使えた」が食い違う）

### 要件 3: 結果の確認（店側の1画面）

**目的:** 店主として、出したオファーの配信数・開封数・来店数と、配信がどこまで進んだかを1画面で知りたい。それにより、次に「残席0」を押すべきかを判断できる

#### 受け入れ基準

1. 店側の画面は、進行中または直近に終了したオファーの配信数・開封数・来店数を1画面に表示すること［段1］
2. 店側の画面は、基準1の数字と並べて反応数（「行きます」を押した客の数。表示に加えるのは AI判断）を表示すること［段1］
3. 配信数は、通知の送信がプッシュサービスに受け付けられた件数（定義は AI判断）であること［段1］
4. 客が同じオファーの画面を初めて開いた時、システムは開封数を1増やし、同じ客の2回目以降は増やさない（同じ客は1回だけ数えるのは AI判断）こと［段1］
5. 客が同じオファーで初めて「特典を使う」を押した時、システムは来店数を1増やし、同じ客の2回目以降は増やさない（同じ客は1回だけ数えるのは AI判断）こと［段1］
6. 店側の画面は、店主の操作なしに数字を取り直す（AI判断）こと［段1］
7. 店側の画面が数字を取り直す間隔は、10秒（AI判断）以下であること［段1］
8. 店側の画面は、今何波目まで出したか・配信総数の上限・次の波の判定までの残り時間（AI判断）を表示すること［段1］

補足:

- 開封と来店の数え方は intent 基準4で要件の段に回されたもの。来店は「客が特典を使う操作をした時点」（intent の例のまま）。用語の定義は「はじめに」
- 基準2の理由: 反応で次の波が止まる（要件7）ので、店主が「なぜ波が止まったか」を画面で読めるようにする。intent 基準4の3つの数字に足したもの
- 基準7は第1周の「変わってから反映されるまで10秒以内［段5］」を、システムが自分で決める間隔（段1で検査できる形）に言い直したもの。実際の反映の遅れは間隔に通信の時間が乗る

### 要件 4: 客の嗜好の登録（入口の LLM）

**目的:** 客として、自然文で嗜好を書くだけで登録したい。それにより、合わない店の通知を受けずに済む

#### 受け入れ基準

1. 客が自然文の嗜好を送信した時、システムは OrcaRouter 経由の LLM でそれをジャンル一覧・予算上限・アレルギー一覧の3項目に構造化すること［段1］
2. 構造化の結果は、ジャンルとアレルギーが設計の段で決める語彙表（語彙表を持つのは AI判断）の値だけからなり、予算上限が0以上の整数か未指定であること［段1］
3. 構造化の結果が基準2の検査に落ちた場合、システムは登録を保存せず、落ちた理由を添えて客に書き直しを求める（本人選択）こと［段1］
4. LLM の呼び出しが失敗するか10秒（AI判断）以内に返らなかった場合、システムは登録を保存せず、客にもう一度送るよう求めること［段1］
5. 送信された自然文が空または空白だけの場合、システムは LLM を呼ばずに入力を求めること［段1］
6. 登録が済んだ時、システムは客の画面にジャンル一覧・予算上限・アレルギー一覧の3項目を、それぞれ日本語の見出し（「ジャンル」「予算の上限」「アレルギー」。見出しの語は AI判断）を付けた文字として表示すること［段1］
7. 基準6の表示で、システムは構造化の結果を JSON などの生データのまま出さないこと［段1］
8. 客の登録では、システムは氏名・メールアドレス・電話番号などの本人を特定する情報を求めない（AI判断）こと［段1］
9. 構造化が済んだ後、システムは構造化に使った自然文の原文を保存しない（AI判断）こと［段1］
10. 客が嗜好を登録し直した時、システムは以前の嗜好を新しい結果で置き換える（AI判断）こと［段1］

補足:

- 基準3は intent 基準13で「本人がまだ決めていない」とされ、要件の段の第1周のあとに本人が選んだもの。選ばなかった案: 嗜好なし（ジャンル・予算・アレルギーとも未指定）で登録する——登録は必ず済むが、アレルギーを取りこぼした客が配信対象に残る（甲殻類アレルギーの客に甲殻類の店のオファーが届く）。語彙表に無い値を「捨てて残りで登録」しないのも同じ理由
- 基準2の検査は「形式（3項目・型）」と「内容（語彙表にある値か）」の2つ。intent 基準13で要件の段に回された「検査の中身」への答え
- 基準6・7は第1周の「人が読める形で表示する」を検査できる形に分けたもの（F2）。未指定の項目は「指定なし」と表示する（AI判断）

### 要件 5: 客の位置

**目的:** 客として、常時追跡されずに、近くの店からだけ通知を受けたい。それにより、電池と気持ちの負担なく使える

#### 受け入れ基準

1. 登録時、客はブラウザの位置取得を1回使うか、手で地点を指定するかのどちらかで位置を登録できること［段1］
2. 位置が登録されていない客を、システムは配信の対象にしないこと［段1］
3. 客が自分の画面で「位置を更新」を行った時、システムは登録した位置を新しい位置で置き換える（AI判断）こと［段1］
4. 相手の絞り込みで、システムは客が最後に登録した位置を使う（「近く」は登録した位置で判定する。AI判断）こと［段1］
5. 客の画面が開いていない間、システムは位置を取得しないこと［段5］

補足:

- 持ち越し「『近くにいる』がいつの位置か」への答え。選ばなかった案: 客の画面を開くたびに位置を取り直す（通知を開く時点では既に配信済みなので絞り込みには効かず、取得の許可を毎回求めることになる）
- デモでは、客が会場で「位置を更新」を1回押せば店の近くにいることになる

### 要件 6: 届ける相手の絞り込み（決定論）

**目的:** 店主として、徒歩圏にいて嗜好の合う客だけに届けたい。それにより、無駄な通知と合わない客の不快を減らせる

#### 受け入れ基準

1. オファーが作成された時、システムは店から直線距離で800 m（分速80 m×10分。AI判断）以内に登録位置がある客だけを候補にすること［段1］
2. 客のジャンル一覧が空でない場合、システムは店のジャンルがその一覧に無い客を候補から除く（一覧が空なら絞らないのは AI判断）こと［段1］
3. 客の予算上限が指定されている場合、システムは店の目安の客単価がその上限を超える客を候補から除く（未指定なら絞らないのは AI判断）こと［段1］
4. 客のアレルギー一覧と店のアレルゲン一覧に共通の品目がある場合、システムはその客を候補から除くこと［段1］
5. 通知の購読が無い客を、システムは候補から除くこと［段1］
6. システムは候補を店からの距離が近い順（同じ距離なら登録が古い順。並べ方は AI判断）に並べ、同じ入力に対して毎回同じ順を返すこと［段1］
7. 絞り込みと並べ替えの間、システムはモデルの推論を1回も呼ばないこと［段1］
8. 候補が0人の場合、システムはオファーを配信数0のまま終了にする（AI判断）こと［段1］
9. 候補が0人の場合、システムは対象がいなかったことを店側の画面に表示すること［段1］

補足:

- 「合う」は本人選択の「ジャンル・予算・アレルギー」の3つを全部満たすこと。スコアづけ（ジャンル一致度・通知疲労度など）は intent の「やらないこと」にあるので持たない
- 徒歩圏の範囲は intent 基準6で要件の段に回されたもの。たたき台の「分速80 m」を使い、時間は10分にした。反応を「行きます」にした（要件7）ので、徒歩圏の広さは次の波の判定の速さに影響しない
- 店側にジャンル・目安の客単価・アレルゲン一覧を持たせる（要件12）

### 要件 7: 段階配信と上限での自動停止（自律の見せ場）

**目的:** 店主として、必要な分だけ通知が広がり、上限で勝手に止まってほしい。それにより、過剰配信を防ぎながら手を離せる

#### 受け入れ基準

1. オファーが作成されて通知文が決まった時、システムは候補の先頭から第1波を配信すること［段1］
2. 第1波の予定人数は10人（AI判断）であること［段1］
3. 各波（第1波を含む）で実際に配信する人数は、その波の予定人数・未配信の候補の数・配信総数の上限までの残りの3つのうち最も小さい値であること［段1］
4. 配信総数の上限は、空席数×4（倍率は AI判断）であること［段1］
5. 次の波を出すかの判定で、システムは「反応」を、客がオファー画面で「行きます」を押すこと（本人選択）として数えること［段1］
6. 前の波から待ち時間（既定180秒。AI判断）が過ぎた時、その待ち時間の間に反応が1件も無ければ、システムは次の波の予定人数を前の波の予定人数の2倍（倍率は AI判断）として配信すること［段1］
7. 待ち時間の間に反応が1件以上あった場合、システムは次の波を出さず、次の待ち時間が過ぎた時に、その間の反応だけを数えて改めて判定すること［段1］
8. 配信総数が上限に達した時、システムは店主の操作なしにそれ以上の配信を止めること［段1］
9. 上限で配信が止まった後も、システムは有効期限か「残席0」までオファーを進行中のままにすること［段1］
10. 未配信の候補が尽きた時、システムは以後の波を出さないこと［段1］
11. システムは、同じ客に同じオファーの通知を2回以上配信しないこと［段1］
12. 第1波の予定人数・待ち時間・倍率・上限の倍率は、コードを変えずに設定値で変えられる（AI判断）こと［段1］
13. 波の判定と配信は、店主や運用者の操作なしに進むこと［段1］

補足:

- 反応の定義は intent 基準8で本人がまだ決めていなかったもので、要件の段の第1周のあとに本人が「行きます」を選んだ。選ばなかった案: 通知の開封を反応にする（広がりは早く止まるが、開いただけの客で止まる）／来店を反応にしたまま待ち時間を徒歩の時間に合わせて伸ばす（第1周の設計者の既定。徒歩圏800 m に対し待ち時間180秒では最初の来店より先に時計だけで波が広がる、と反論役が指摘した）。「行きます」は通知を見たその場で押せるので、待ち時間180秒は歩く時間に縛られない
- 基準3・4は第1周の F1（空席数1〜2で第1波の10人が上限4〜8を超える）と F3（候補が10人未満のとき第1波が何人か）を1箇所で閉じたもの。例: 空席2・候補30人なら第1波は8人で上限に達して止まる／空席5・候補7人なら第1波は7人で候補が尽きる／空席20・候補100人なら 10→20→40→10 で上限80に達する
- 基準6の「予定人数」を実際の人数でなく前の波の予定人数の2倍にするのは、候補や上限で頭打ちになった波の後も、広がり方が 10→20→40 と読めるようにするため（AI判断）
- 待ち時間180秒はたたき台の「3分無反応なら第2波」から。デモでは設定値（基準12）で短くする
- 満席での停止は要件2の手動だけ（本人選択）。基準9はその決定を守るためのもの

### 要件 8: オファーの有効期限

**目的:** 店主として、出しっぱなしのオファーが時間で終わってほしい。それにより、止め忘れても古い特典が使われ続けない

#### 受け入れ基準

1. オファーが作成された時、システムは作成時刻から30分（AI判断）後を有効期限にすること［段1］
2. 有効期限が過ぎた時、システムは店主の操作なしにオファーを終了にして以後の波を出さないこと［段1］
3. 有効期限が過ぎたオファーで客が「特典を使う」を押した場合、システムは特典を無効として扱い来店に数えない（要件2基準4と同じ扱い。AI判断）こと［段1］
4. 客のオファー画面は、有効期限の時刻を表示する（AI判断）こと［段1］
5. 有効期限の長さは、コードを変えずに設定値で変えられる（AI判断）こと［段1］

補足:

- 持ち越し「オファーの有効期限」への答え（たたき台の既定30分から）。店主が期限を選ぶ画面は作らない（操作を短く保つため。AI判断）

### 要件 9: 通知文の生成（出口の LLM）と定型文

**目的:** 店主として、店と特典に合った通知文を自分で書かずに出したい。それにより、送信までの操作が増えない

#### 受け入れ基準

1. オファーが作成された時、システムは OrcaRouter 経由の LLM で通知文（見出しと本文）をオファーごとに1回（客ごとに変えないのは AI判断）生成すること［段1］
2. 通知文の検査で、システムは見出しが30字以内・本文が80字以内・店名と特典の名前を含む・改行を含まない、の4点（検査の中身は AI判断）を見ること［段1］
3. 生成した通知文が基準2の検査に落ちた場合、システムは承認を待たずに定型文へ切り替えて配信を続けること［段1］
4. LLM の呼び出しが失敗するか10秒（AI判断）以内に返らなかった場合、システムは定型文へ切り替えて配信を続けること［段1］
5. 定型文は、店名・特典の名前・有効期限の時刻を含む固定の型（AI判断）であること［段1］
6. オファーごとに、システムは通知文が LLM の生成か定型文かを記録する（AI判断）こと［段1］
7. 通知文の生成で、システムは客の登録内容（嗜好・位置）を LLM に渡さない（AI判断）こと［段1］

補足:

- 出口で検査に落ちたら定型文に切り替えて配信を続けるのは本人選択（intent 基準13）。検査の中身は要件の段に回されたもので、基準2が答え
- 通知文をオファーごとに1回にするのは、配信先の人数分の LLM 呼び出しを避ける（コストと第1波までの時間）ため

### 要件 10: Web プッシュの受信

**目的:** 客として、アプリを入れずに実機で通知を受け取りたい。それにより、登録のハードルが下がる

#### 受け入れ基準

1. 客が通知の許可を与えた時、システムはその端末の購読を保存して配信の対象にすること［段1］
2. 客が許可を与えなかった場合、システムは登録自体は完了させる（AI判断）こと［段1］
3. 客が許可を与えなかった場合、システムは客の画面に固定文「通知は届きません。ブラウザの設定で通知を許可してから、もう一度ボタンを押してください」（文言は AI判断）と、許可を求めるボタンを表示すること［段1］
4. 配信時、通知はプッシュサービスを経由して客の端末に届くこと［段3］
5. 客が届いた通知をタップした時、そのオファーの画面が開くこと［段1］
6. 通知の送信がプッシュサービスに拒否された（購読の失効）場合、システムはその購読を削除して以後の配信対象から外す（AI判断）こと［段1］
7. iPhone の Safari で客の画面を開いた場合、システムは「ホーム画面に追加してから、ボタンを押して許可する」案内を表示すること［段1］
8. システムは、客がボタンを押した時だけ通知の許可を求める（AI判断）こと［段1］
9. デモの実機（Android 1台と iPhone 1台）で、本人が通知が実際に届くことを確かめること［段5］

補足:

- 経路が Web プッシュであること、実機が Android と iPhone の両方であること、iPhone に案内を入れることは本人選択（intent 基準10）
- 基準3は第1周の「許可の方法を表示する」を固定文にしたもの（持ち越し3件目）。許可の手順はブラウザや OS ごとに違うので、文言は「設定で許可してからボタンを押し直す」までにとどめ、端末ごとの手順は書かない
- 基準4は実機とプッシュサービスを通さないと分からないので段3。基準5は通知の中身（開く URL）の検査で決められるので段1。第1周ではこの2つを1行の段3にまとめていた（持ち越し4件目）
- 基準8は iPhone の制約（許可は利用者が直接操作したときだけ求められる）を全端末に揃えたもの

### 要件 11: 客のオファー画面と「行きます」・特典の使用

**目的:** 客として、届いたオファーの中身を見て、行くつもりを店に伝え、店で特典を使いたい。それにより、店側では反応と来店が数えられる

#### 受け入れ基準

1. 客が通知をタップした時、システムは店名・特典・有効期限・「行きます」ボタン・「特典を使う」ボタンを載せたそのオファーの画面を開くこと［段1］
2. 客が進行中のオファーの画面で「行きます」を押した時、システムはそれを反応として記録すること［段1］
3. 同じ客が同じオファーで「行きます」を2回以上押した場合、システムは反応を1件だけ数える（AI判断）こと［段1］
4. 「行きます」を押した後、システムは画面に押したことを表示する（AI判断）こと［段1］
5. 客が進行中のオファーの画面で「特典を使う」を押した時、システムはそれを来店として記録すること［段1］
6. 「特典を使う」を押した後、システムは画面に使用済みと表示すること［段1］
7. 客が「行きます」を押していない場合でも、システムは「特典を使う」を受け付ける（AI判断）こと［段1］
8. 終了したオファーの画面を開いた場合、システムは終了した旨を表示すること［段1］
9. 終了したオファーの画面で、システムは「行きます」と「特典を使う」のどちらも押せなくすること［段1］
10. そのオファーの配信先でない客がオファー画面の URL を開いた場合、システムは中身を表示せず「行きます」も「特典を使う」も受け付けない（AI判断）こと［段1］

補足:

- 「行きます」は本人選択の反応の定義（要件7基準5）を客の画面に置いたもの。基準7の理由: 通知を見てそのまま店に来た客が特典を使えないと、来店数が実態より少なくなる
- 基準10の理由: URL が共有されただけで特典が使えると、来店数が配信の効果を表さなくなる。デモで見せる数字の意味を守るため

### 要件 12: 店側の保護と初期データ

**目的:** 店主として、自分の店の操作を他人にされたくない。それにより、いたずらのオファーで客の信頼を失わない

#### 受け入れ基準

1. 店側の画面と操作は、店ごとに発行した秘密の鍵を持つ要求だけが使える（本人選択。ログイン画面は作らない）こと［段1］
2. 鍵が無い、または一致しない要求に対し、システムは店のデータを返さず操作も受け付けないこと［段1］
3. 店のデータ（店名・位置・ジャンル・目安の客単価・アレルゲン一覧・特典プリセット3つ・鍵）は、投入用の種データから作れる（AI判断）こと［段1］
4. 客の画面は、その客の端末に紐づく鍵を持つ要求だけがその客の登録内容を読める（AI判断）こと［段1］
5. 鍵は、リポジトリのコードに書かず設定または投入時に与えること［段2］

補足:

- 持ち越し「店主のログインと初期設定」への答え。店側を鍵で守りログイン画面を作らないのは、要件の段の第1周のあとに本人が選んだ（選ばなかった案: パスワードのログイン画面のみ）。**パスワードのログイン画面＋Turnstile へ段階的に広げることは本人が検討中で、今回の必須ではない**（本人発案）。設計の段では、鍵の形と、後からログイン画面を足せる置き方（撤退しやすさ）を書く
- 初期設定の画面は作らない（AI判断。本人選択の「プリセット3つから1タップ」は使う側の要件で、登録する側の画面は求められていない）。基準3の種データがその代わり
- ボット対策（チーム案の Turnstile）は設計の段で検討する

### 要件 13: 効果を示す数字の記録

**目的:** 本人として、審査員に見せる数字の候補を後から数えられるようにしたい。それにより、提出前にどの数字を出すかを選べる

#### 受け入れ基準

1. LLM を呼び出すたびに、システムは用途（入口か出口か）・OrcaRouter が返す実費・所要時間・成功か失敗か（記録する項目は AI判断）を記録すること［段1］
2. オファーごとに、システムは作成時刻と第1波の送信が完了した時刻を記録すること［段1］
3. オファーごとに、システムは「残席0」による人手の停止があったかどうかを記録すること［段1］
4. 記録した数字は、店側の画面のオファーの詳細（置き場所は AI判断）で読めること［段1］
5. オファーを出してから第1波の送信が完了するまでは、30秒（AI判断）以内であること［段3］

補足:

- どの数字を審査員に見せるかは本人が決める（intent「本人が決めること」）。この要件は候補を数えられる形にしておくだけ。候補: 配信数・反応数・開封数・来店数（要件3）、LLM の1件あたり実費、第1波までの時間、配信の判断に人が手を入れた割合（承認なしなので基準3の停止だけが人手）
- 基準5が段3なのは、LLM（要件9）とプッシュサービスの応答時間を含むため（「はじめに」の規則）

### 要件 14: 構成と提出の条件

**目的:** 本人として、大会の必須条件と本人の注文した構成を満たした形で提出したい。それにより、審査の対象から外れない

#### 受け入れ基準

1. ウェブアプリの枠組みは Next.js（本人発案）であること［段2］
2. 提出版は Cloudflare 上（本人発案）で動いていること［段3］
3. LLM の呼び出しは、入口（要件4）も出口（要件9）もすべて OrcaRouter の API（本人選択）を経由し、他の LLM 提供元へ直接つながないこと［段1］
4. 公開するリポジトリには、API キー・通知の鍵・店と客の鍵・客の登録内容・購読情報（大会の提出要件「API キー・個人データ」を基に品目を AI判断で補った）を含めないこと［段2］
5. 動かすのに必要な環境変数の名前と手順は README に書かれ、チームD の他のメンバーが手元で動かせること［段5］
6. 提出は GitHub の public リポジトリ（AI判断・要確認）で行うこと［段5］

補足:

- 基準4は本人判断に回った指摘（intent-c3 の F1「秘密情報の基準に帰属の印が無い」）への答え。基準は大会の要件そのものだが、品目の列挙は本人の確認を経ていない
- 基準5は intent 基準17（AI判断として承認済み）を写したもの
- 基準6は持ち越し「提出の形の帰属」への答え。選ばなかった案: Google Drive で閲覧権限を付けたリンク（01_要件が認める道。public にしないので秘密情報の扱いは緩むが、リポジトリを `~/src/product/ai-hack` に置くと決めた本人選択と GitHub の流れが自然）
