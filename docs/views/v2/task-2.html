web/lib/http/guards.ts

不具合重さ: 中確度: 確実行33・F1

セッションの有効期限が壊れた（パース不能な）値のとき、identifySession は「期限切れではない」側へフェイルオープンする——new Date(壊れた文字列).getTime() は NaN になり、NaN <= now は常に false なので期限切れ判定が発火せず、そのままセッションを有効として扱ってしまう。

if (new Date(row.expires_at as string).getTime() <= deps.clock.now().getTime()) return null;
web/lib/http/guards.ts:19 /** セッションの Cookie を SHA-256 にして探す。無い・でたらめ・期限切れなら null（401 の元）。 */

getTime() の結果を変数に取り、Number.isFinite で壊れた日付を明示的に検出して null（=期限切れ扱い）へ倒す。すぐ上の doc コメント自身が「期限切れなら null」と契約を書いており、コードがその契約を満たしていない。

自分で経路を追い、崩せなかった（AGREE）。row.expires_at が null のときは new Date(null)=0 で偶然フェイルクローズするため、壊れた文字列のケースだけが素通りする点が追加確認で補強された。

改善提案重さ: 中確度: 高確率行103・F3

multipart の壊れた本文は明示的に UNREADABLE_BODY（→400 bad_format）へ倒すのに、JSON の本文が壊れているときだけ黙って {} に差し替える。スキーマの無い入口（config.input 未指定）ではこの {} がそのまま素通りし、スキーマのある入口でも実際の原因（本文が壊れている）とはずれた reason が返る。

// JSON になっていない本文は「項目が何も無い」として扱い、スキーマの検査に判定を任せる。 return JSON.parse(text);
web/lib/http/defineRoute.ts:90 return Object.fromEntries((await req.formData()).entries()); } catch { return UNREADABLE_BODY;

multipart と同じ扱いに揃え、JSON.parse の catch でも UNREADABLE_BODY を返す。反論役の指摘で severity を medium へ引き上げた——スキーマの無い入口ができた時点で壊れた JSON が検査を一切通らずに素通りする経路が確認でき、r29 の38行「本文のある入口の全部で ok:false」という受け入れ検査の前提を壊しうる。
