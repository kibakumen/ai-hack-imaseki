① ファイル構成の計画（境界）

客・店・運営の三者の画面と API を1つの Next.js アプリ web/ に書き、Cloudflare Workers に載せる（AI判断）。判断はすべて lib/domain/（副作用なし）に置き、画面の部品はサーバーが返した「表示の種類」を描くだけ。外のサービス（AI・地図・プッシュ・カード・ファイル・人かどうかの確かめ・ログ）は lib/adapters/の1サービス1ファイルだけが触る。

③ ゲートの3つのコマンド

種類コマンド（配列）
型検査["pnpm","exec","tsc","--noEmit","-p","tsconfig.json"]
lint["pnpm","--dir","web","exec","eslint","."]
テスト["pnpm","exec","vitest","run"]
  • 直下の tsconfig.json は web/** と tests/** の両方を検査（demo/・sprint/・生成物は除く）
  • 直下の vitest.config.ts は web/**/*.test.{ts,tsx} と tests/acceptance/v2/**/*.test.{ts,tsx} の両方を走らせる
  • lint は今のまま web/ の中だけに掛ける（本人選択・2026-09-20・18節。第1周の監査「受け入れ検査フォルダも対象に」を、理由（強制する境界が tests/ には無い）を示して据え置いた）
  • 受け入れ検査はタスクごとに走る（第5周のあとの直し）: 各ブロックは describeTask(タスク番号, 名前, 本体) を通す。.dev/runs/v2/task-<番号>.json（着手の記録・進行役の道具のみが作る）が無ければそのブロックは飛ぶ。着手の記録のフォルダそのものが無い手元では全部走る

④ 監査の指摘（第7周・分担A/B/C）を該当する節の横に

F1defect重さ: medium確度: 高確率／分担A

該当する節: 「受け入れ検査をタスクごとに走らせる」（describeTaskの仕組み）

タスク番号の食い違いなどで対象ブロックが全部 skip されても、ゲート（gate-code.mjs）は終了コードだけで通過を決めるため、「何も実行されていないのにゲート通過」が構造的に起こり得る（設計書は「飛ばしたことは隠れない」と書くが、それを見るのは終了コードを見る仕組みではない）。

design.md 114行「飛ばしたブロックは Vitest の出力に skipped として数が出るので、飛ばしたことは隠れない。」
gate-code.mjs 33行「if (result.status === 0) return { shown, error: null };」

直し方の提案: テストコマンドを --reporter=json 等で走らせ、着手中タスクのブロックが1件以上「実行された（skipでない）」ことを不合格条件に足す。

F2improvement重さ: low確度: 高確率／分担B

該当する節: 「入口（API）の一覧」の「登録の入口」の分類

要件書の用語「登録の入口」は「客の登録と店の登録だけが入る」と閉じて定義されているが、design.md はこの同じラベルを、ログイン・ログアウト・公開設定値取得（GET /api/config/public）まで含む5つの入口の分類名として、帰属の印を欠いたまま無印で再利用している。

requirements.md 65行「まだ要求の主を持たない人が最初に使う要求のまとまり（語はAI判断）。客の登録…と、店の登録…だけが入る。」
design.md 331行「登録の入口｜POST /api/register/customer・…・POST /api/auth/login・POST /api/auth/logout・GET /api/config/public…」

直し方の提案: 見分けの5つ目のカテゴリ名を「無記名の入口」など要件書と別の語にする。あるいは requirements.md 側に、設計の段で同分類に含める場合がある旨を申し送る。

F3defect重さ: low確度: 高確率／分担C（利用シーンを歩く）

該当する節: 「利用シーンを画面の上で歩く」のS1（客がはじめて使う場面）5歩目

S1の5歩目は、田中さんが初回受け取り直後に「通知を受け取る」を押して許可する前提で書かれているが、design.md自身が別の場所で、プッシュの仕組みが無いブラウザ（ホーム画面未追加のiPhone Safariが明示例）では「通知を受け取る」ボタン自体が出ず説明文だけになると定めている。田中さんの1歩目（intent.md）にはホーム画面への追加が出てこない。

design.md 496行「プッシュの仕組みが無いブラウザ（iPhone の Safari でホーム画面に追加していない場合など）では、許可を求めるボタンを出さず…」
design.md 551行「焼肉店のカードの「この店に行く」→確保中の表示…その上に通知の説明が1回だけ出る→「通知を受け取る」」

直し方の提案: S1の5歩目に条件分岐を明記する。実害は無い（開けば分かるフォールバックが既にある）が、design.md自身の歩きが自身の制約と矛盾している点は直すべき。

F4improvement重さ: low確度: 高確率／分担C

該当する節: 「利用シーンを画面の上で歩く」のS1・7歩目／要件3の補足（人数の初めの値）

取得画面の人数は「初めの値を置かない」方針（S2の人数変化の見落とし防止のため）だが、S1の7歩目のように人数が変わっていない再検索（ジャンルだけ和食に変える）でも同じ手間で人数を打ち直させており、方針の根拠が当てはまらない場面にも一律適用されている。

design.md 553行「取得の画面でジャンルを「和食」に変え（その回だけ）、人数2を入れて探す→和食の店を受け取る」
